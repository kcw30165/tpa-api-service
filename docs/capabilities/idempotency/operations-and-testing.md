# Idempotency Operations, Configuration, and Testing

## Consolidation release gates

- P0 documents and approves the target before production code changes.
- P1 adds session-context-neutral shared contracts without endpoint behavior changes and proves the model has no feature or session-type dependency.
- P2 adds the single shared Redis implementation.
- P3 through P6 migrate complete action families.
- P7 removes stale feature-specific infrastructure and proves its absence.
- P8 performs formatting, compilation, focused behavior, concurrency, crash-boundary, compatibility, and release validation.

For every deterministic terminal outcome in anonymous, pre-authentication, authenticated, and service-context integrations, first-call and replay HTTP status and body must be equal, while protected operations and external side effects execute exactly once. Corrupt or unsupported snapshots fail closed.

See [Shared Idempotency Consolidation Implementation Plan](shared-idempotency-consolidation-plan.md).


## 1. Configuration reference

Review per action:

- Enabled/required behavior
- Key header name (`Idempotency-Key` at the BFF boundary)
- Key format and length
- Redis application/capability prefix
- Action name
- TTL
- Canonical hash version
- Replay snapshot schema/version
- Known-failure behavior
- Unknown-outcome/reconciliation policy
- Public error and HTTP mapping

## 2. Redis operational model

Idempotency adapters use atomic create/reserve behavior, JSON serialization, deterministic key factories, and TTL. Operational checks include:

- Redis Sentinel health
- SSL/mTLS and credentials
- Key prefix/environment isolation
- Command timeout and pool capacity
- Memory/eviction policy
- TTL distribution
- Serialization/deserialization errors
- Clock synchronization
- Failover behavior

Do not bulk-delete broad auth/idempotency prefixes during support. Any administrative cleanup must be capability/action-scoped, authorized, and audited.

## 3. Troubleshooting runbook

### Missing key

The client omitted `Idempotency-Key` or sent blank input. Return the standard missing-key validation error; do not generate a server-side substitute.

### Duplicate remains “in progress”

Check operation duration, downstream timeout, application crash, Redis record status/timestamp, and TTL. Do not delete the record until you know whether a side effect occurred.

### Same key is rejected after request edit

This is expected when the canonical request hash changed. The client must generate a new key for a new logical request.

### Completed operation executes twice

Investigate:

- Reservation not atomic
- Side effect happened before reservation
- Different action/key namespace
- Different canonical hash/key generated by client
- Record expired too early
- Internal retry bypassed coordinator
- Replay snapshot load/deserialization failed and code fell through to execution

Treat duplicate customer-impacting mutation/message as an incident.

### Replay result differs from original

Check snapshot schema, non-deterministic fields, omitted workflow data, normalization, header safety filtering, and mapper version compatibility. Replay should preserve business meaning while excluding secrets.

### Record is `UNKNOWN_OUTCOME`

Use the operation-specific reconciliation procedure. Check downstream/provider evidence using request ID and safe references. Do not simply change status to failed or delete the record.

### Redis unavailable

The service cannot safely guarantee deduplication. Follow the operation's fail-closed/failure contract. Do not bypass idempotency for critical mutations merely to restore availability.

### Unexpected hash mismatch

Compare canonicalization rules, mapper versions, field ordering, trimming/case behavior, null/empty treatment, and client payload. Never log the clear sensitive inputs to compare them.

### TTL expires before retry

Review operation timeout, retry/backoff, client retry interval, and safety margin. Increasing TTL changes retention and key-reuse behavior and requires review.

## 4. Logging and observability

### Safe fields

- `X-Request-Id`
- Action
- Idempotency outcome/status category
- Retry/replay indicator
- Record age/TTL bucket
- Duration
- Exception type
- Safe workflow status

### Forbidden fields

- Idempotency key where organizational policy treats it as sensitive
- Request hash when it can become a correlatable fingerprint
- Canonical input
- Password, OTP, identity, destination, account data
- Session/CSRF token
- Replay body containing customer/security data
- Redis credentials or full raw key

Recommended events:

```text
idempotency.reserved
idempotency.duplicate_in_progress
idempotency.completed
idempotency.replayed
idempotency.key_reused
idempotency.failed
idempotency.unknown_outcome
idempotency.snapshot.invalid
```

Prefer a one-way/safe internal record reference if operations needs correlation beyond request ID.

## 5. Metrics and alerts

Track by action and environment:

- Reservations
- Completed results
- Completed replays
- Duplicate-in-progress outcomes
- Key-reuse mismatches
- Failed records
- Unknown outcomes
- Snapshot serialization failures
- Redis latency/failure
- Record processing age
- TTL expiry distribution

Alert on unknown-outcome spikes, stuck processing records, duplicate side-effect incidents, snapshot failures, abnormal key-reuse rates, and Redis availability degradation.

## 6. Test strategy

### 6.1 Key and action tests

- Missing/blank key
- Minimum/maximum length
- Unsafe characters/delimiters
- Stable action serialization
- Different actions produce separated Redis keys
- No PII in generated keys

### 6.2 Canonical request hash tests

- Same logical request yields same hash
- Field order does not change hash where order is non-semantic
- Material field change changes hash
- Trimming/case/null/empty rules
- Collection ordering rules
- Versioned canonical representation
- Clear sensitive values absent from logs/exceptions

### 6.3 Redis adapter tests

- Atomic first reservation
- Existing record with same/different hash
- Complete/fail/unknown updates
- Load/delete according to policy
- TTL applied to each write/update
- JSON round trip
- Safe exception translation
- Concurrent `setIfAbsent`
- Sentinel failover in integration environments

### 6.4 Coordinator tests

- `STARTED`
- `DUPLICATE_IN_PROGRESS`
- `COMPLETED_REPLAY`
- `KEY_REUSED_WITH_DIFFERENT_REQUEST`
- `FAILED_EXISTING`
- `UNKNOWN_OUTCOME_EXISTING`
- Port failure before side effect
- Completion-record failure after side effect
- Snapshot serialization failure

### 6.5 Replay snapshot tests

- Exact approved result fields
- Workflow `nextStep`
- Masked destination/timing values
- Allowed safe headers only
- Reject `Set-Cookie`, `Authorization`, XSRF/session/token headers
- No OTP/password/raw PII
- Schema compatibility or deliberate invalidation behavior
- Corrupt snapshot fails safely without re-executing side effect

### 6.6 Concurrency tests

- Many identical concurrent requests: one executes
- Same key with different hashes: one owner, others rejected
- Different keys for same resource with completion lock
- Process crash after reservation
- Crash after external side effect
- Crash after completion before response
- Lock expiry/ownership behavior

### 6.7 Workflow integration tests

- Login start replay does not recreate flow/destination state
- Login OTP send/resend replay does not resend
- Login OTP verify replay does not create another authenticated session
- Registration start replay does not repeat lookup/message
- Registration OTP verify replay preserves next step
- Registration completion replay does not call TAS/APIM again
- Delivery/APIM timeout becomes unknown according to policy
- Missing key and mismatch map to approved API errors

### 6.8 HTTP contract tests

- Required `Idempotency-Key`
- Invalid key format
- Duplicate-in-progress HTTP/status/error mapping
- Key-reuse mapping
- Completed replay response shape
- Request ID propagation
- No replayed security headers/cookies

## 7. Failure classification matrix

Maintain an action-specific matrix:

```text
Internal outcome
Application result
Public error code
API status
HTTP status
Retryable by client
Replayable
Reconciliation required
Log severity
Frontend next step
```

Include Redis failure, snapshot failure, and unknown downstream/provider outcomes.

## 8. Release evidence

Each idempotency change should include:

- Action definition and owner
- Canonical hash specification/version
- TTL justification
- Replay snapshot schema and safety review
- Fail-first TDD evidence
- Adapter and coordinator test results
- Concurrency/crash-boundary test evidence
- Downstream idempotency assessment
- Error-mapping matrix
- Redis key/retention impact
- Logging-redaction evidence
- Rollback and reconciliation plan
- Monitoring/alert updates
- Commit message
