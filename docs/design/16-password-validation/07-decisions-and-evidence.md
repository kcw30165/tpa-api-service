# 07 Decisions, evidence and implementation checks

## Approved decision register
D01 One shared password-validation endpoint; Personal Information initially, future investment/fund-switch consumers unsupported now.
D02 Bind to authenticated session, selected account, purpose and exact reviewed changes; FE sends proposed operation payload at confirmation.
D03 TTL 5 minutes; one active token per session/account/purpose; successful confirmation replaces old token; other scopes coexist.
D04 First authenticated submission consumes, including validation failure, payload mismatch and malformed JSON. Token in header; ownership/session/CSRF/account checks precede consumption.
D05 Downstream owns password failure counting and lock threshold; no local five-attempt rule or fail-count exposure.
D06 Wrong password returns code only. Locked account invalidates current session and cookie; cookie always cleared even if invalidation fails, with technical failure reported.
D07 No accountEnv in TRPPwdValidation body/header; business HTTP 200; data exactly one item on empty-error path; unregistered cust-id -> 503.
D08 No automatic password-validation retry. No new mutation result replay. Consumed tokens never authorize another execution.
D09 POST /api/v1/password-validation; X-Password-Validation-Token; token/expiresInSeconds result; configured login password lengths, no trimming/case conversion or registration complexity.
D10 JSON object order irrelevant; arrays/types/null presence significant; no silent value normalization.
D11 Approved HTTP matrix: wrong password 401; locked 423; invalid authorization 403; invalid request 400; technical failures 503; throttle 429.
D12 Username-wide configurable 10 requests/60 seconds across sessions/accounts/purposes, independent of TAS lock counting.

### Gate resolution status (M0 corrective passes, source-grounded -- E4)

This pass read full method bodies and Lua scripts (E4) to resolve gates at the design level with exact source references. No code was changed; these are design decisions, not implementation-complete claims. G1 and G4 below were further corrected in a second corrective pass after the independent reviewer returned CHANGES REQUIRED on commit 5540abac, identifying a blocking session-resurrection race (G1), a major grant-key account-scoping gap (closed in Section 6 of 01-solution-design.md), a major logging-exclusion robustness gap (G4), and a major response-type contradiction (closed in 02-api-contract.md). G1 and G4 were corrected a third time after the independent reviewer returned CHANGES REQUIRED on commit a6f8adb2, finding the second pass's revision-bump fix insufficient on its own (the blind `loadAndTouch`/`port.touch` path can still resurrect state regardless of revision) and finding the second pass's header-logging fix still configuration-dependent. G1 was corrected a fourth time after the independent reviewer returned CHANGES REQUIRED on commit 72d26782, finding that routing loadAndTouch and persistTerminal through the unmodified existing CAS method could not work at all, because that method has a hardcoded eligibility check that rejects before mutating whenever a session is not usable, and its Lua script cannot express a TTL different from whatever is already stored.

- G1 (Storage): M1.5 APPROVED at the D16 anchor; M2 APPROVED at the D17 anchor; M3 APPROVED at the D19 anchor. The generalized writer, additive grant-only write-point guard, grant replacement/consumption and username throttle are mapped in Section 6 of 01 and Section Throttle of 04. `AuthenticatedSessionConditionalWriteRedisTest` exercises actual protected Redis writes, PTTL/deadlines, races, skew, conflict exhaustion and uncertain acknowledgements with isolated Redis 8.0.5. - G3 (Limits): RESOLVED for the local M3 path, not deployment overrides. Login bounds are read from `auth-workflows.login.credential.password-min-length`/`password-max-length` (env `LOGIN_PASSWORD_MIN_LENGTH`/`LOGIN_PASSWORD_MAX_LENGTH`, defaults 1/128). - G4 (Logging): PARTIALLY RESOLVED, CORRECTED after independent review (now twice). The body-logging reliance on "never configure an endpoint-logging rule for these two paths" plus a config-scan test was insufficient (`AntPathMatcher` wildcard rules could still match without naming them); the corrected design requires a hard, code-level path denylist inside `RequestLoggingWebFilter` that unconditionally overrides any configured rule match for these two exact paths (see corrected Observability section of 04-validation-and-error-handling.md). A second, independent gap was then found in header logging: relying on "never add the token header to the allowlist" plus a config-scan test was equally insufficient, because `buildAllowedHeaders` would still log the header if an operator ever added it to the allowlist in any environment. The corrected design requires a hard, code-level, case-insensitive exclusion of `X-Password-Validation-Token` inside `RequestLoggingWebFilter.buildAllowedHeaders` (or equivalent) that unconditionally overrides any allowlist entry; the config-scan test is now secondary defense-in-depth for both the body and header paths, not the primary control. Redaction still follows the `CaptchaChallengeResponse`-style `<redacted>` `toString()` precedent. `SecurityAuditMetadataSanitizer` remains confirmed as a separate mechanism from `RequestLoggingWebFilter`'s logging path and must not be assumed to cover it.
- G4 M3 implementation evidence: the unconditional method/path and header guards are implemented in RequestLoggingWebFilter and exercised with wildcard rules, allowlisted mixed-case token headers, both body directions and confidential throwable text. The real issuance HTTP chain also runs with wildcard body logging enabled. This closes the BFF guard implementation item, not independent review or external gateway/APIM/deployment logging checks.

D19's M4 gate reuses that matcher at +3. Both matched routes' variant guards and 404/default-firewall rejections require actual HTTP proofs.
