# Shared General Metadata Cache and Resolver Design

**Feature:** 6.14 Account Balance  
**Baseline:** 27/08/2026  
**Status:** Consolidated design baseline, pending repository investigation  

## Key decision

Use one Redis key per requested environment, trust, and policy scope, generated by `RedisCacheKeyFactory`:

```text
<prefix>:general-metadata:<opaque-env-trust-policy-qualifier>
```

This is not a full copy for every possible policy. It is created only for policy scopes actually encountered. It avoids a separate marker, multi-key lifecycle management, and concurrent merging of many policies into one shared document.

## Entry

```json
{
  "requestedScope": "opaque",
  "resolution": "DEFAULT_ALL",
  "metadata": {
    "FUND_PRICE:PRECISION": "6",
    "UNIT_BALANCE:PRECISION": "5",
    "NET_ASSET_VALUE:PRECISION": "2"
  }
}
```

`resolution` is `DEFAULT_ALL` when TAS returned `policy-no=all`, or `POLICY_SPECIFIC` when TAS returned the requested concrete policy. The resolution marker is inside the same entry and shares its lifecycle.

## Why policy-scoped key is safer

TAS decides the effective scope only after receiving the actual policy number. Before calling TAS, Java cannot know whether a policy uses environment/trust defaults or a policy-specific override. A shared environment/trust key alone cannot safely prove applicability for an unseen policy. A small, lazy, per-encountered-policy resolved entry is therefore correct and bounded by active usage and the 20-minute TTL.

## Resolver

```java
public interface GeneralMetadataResolver {
  Mono<GeneralMetadataSet> resolve(
      GeneralMetadataScope scope,
      Set<GeneralMetadataKey> requiredKeys);
}
```

Algorithm:

```text
1. Build the opaque env/trust/policy Redis key.
2. Read Redis.
3. On valid hit, return required metadata.
4. On miss, call TRPGetGeneralMetaData with actual scope and empty filters.
5. Validate every row policy-no is either all or the requested policy.
6. A response mixing all and concrete policy values for the same key is invalid unless TAS later defines precedence.
7. Store the resolved metadata and embedded resolution marker for 20 minutes.
8. If required keys are absent, make a targeted call using the same semantics, merge into the same entry, and reset TTL.
9. Missing after targeted reload is a technical failure.
```

Targeted calls follow the same TAS default-versus-specific behavior.

## Duplicate handling

Uniqueness is `(policy-no, metadata-name, metadata-type)`. Identical duplicates deduplicate; conflicting duplicates fail.

## TTL

```yaml
redis-cache:
  general-metadata:
    ttl: PT20M
```

No startup call, stale fallback, explicit version, or invalidation workflow. After expiry, reload on demand.

## Precision validation

Java displays the precision TAS provides. Validate only that precision is a nonnegative integer representable by the Java formatting API. Do not impose a business maximum or clamp it.

## Concurrency

A single policy-scoped key removes cross-policy merge risk. Investigation must identify whether the project already uses `Mono.cache`, in-flight request coalescing, `setIfAbsent`, CAS, or another single-flight pattern. Until then, the design requirement is: concurrent misses for the same key should ideally coalesce, but correctness must not depend on coalescing because identical successful writes are idempotent.
